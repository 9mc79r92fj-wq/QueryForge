# V2 Reranker 性能分析

## 历史事实（来自 V1 审计归档）

- 交叉编码器：BGE-reranker-base（ONNX，CPU），线程 2、批大小 4
- 首次真实 HTTP 请求（2 个候选）耗时 21,682.167 ms
- 暖机复测：开发预热 34,732.886 ms，测试前再预热 14,473.489 ms，测试 P95 仍为 17,452.847 ms
- 同场次 Adaptive（不含精排）P95 约 17.7 ms

结论：延迟主要来自 CPU 上的交叉编码推理与模型初始化，而不是检索或网络。

## 本轮新增（已实现）

`should_rerank()` 选择性精排策略，触发条件：

```
请求 rerank=1
∧ 剩余延迟预算 ≥ 400ms
∧ 候选数 ≥ 2
∧ 融合分数 Top1 与 Top2 差值 < 0.35
```

跳过原因会写入 `SearchResponse.routing.rerank_reason`，可直接统计触发率。**本轮没有重新做 Profiling**，也没有实现批处理、候选裁剪或量化，因此不宣称延迟改善。

## 预期与约束

- 在 2 vCPU 免费实例上，精排单次仍可能在秒级；因此公网演示默认关闭，仅本地或管理员可选
- 不允许用降低召回换取漂亮延迟；任何优化都要在同一测试集上同时报告 Recall/MRR/NDCG 与 P95
